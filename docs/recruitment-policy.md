# 招聘收录与核查规范

生效日期：2026-09-13。依据用户本轮明确要求，替代旧版“高匹配算法岗位精选”的准入口径。适用于央国企机会池的后续人工及 AI 维护。

## 1. 先识别机会，再安排优先级

候选人是 2027 届应用统计硕士，具备统计建模、算法实习和科研经历。只要专业有报考依据或合理确认空间、工作并非完全不相关、单位和岗位有实际考虑价值，就可以进入机会池；不要求岗位涉及算法、模型、研发或 AI。

覆盖统计/经营分析、银行综合/管培、风险/审计、保险/精算、投研/交易、运营/综合管理、供应链/规划、产品/市场、软件/数据工程，以及原来的技术方向。招聘岗位未达到完全匹配不等于应该删除。优先级用于安排时间，不是准入门槛。

不设 80、100 等凑数指标。不能只列知名集团首页、复制每个省份的相同岗位，或者把同一集团公告的岗位类别拆成多家公司。一个招聘入口可展示多个方向；仅在雇主、资格、流程或职位确实独立且有维护价值时才拆卡。页面数量是卡片/机会入口数，不是独立法人或招聘人数。

## 2. 必须分别记录的证据

| 维度     | 判断要求                                                                                                                            |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| 专业条件 | 明确列应用统计；列统计/数理统计类；具体岗位不限专业；相关专业待确认；条件未读到。前三级只表示存在专业依据，不表示个人资格审核通过。 |
| 招聘批次 | 2027 当届公告、往届依据、届次/入口未核。已结束的 2027 实习不等于 2027 正式校招关闭。                                                |
| 具体机会 | 公告内岗位/职责、工作地点、招聘对象、可以采取的下一步动作。只有集团业务介绍不够。                                                   |
| 用人单位 | 实际签约主体和国资关系；参股、混合所有制不得写成全资央企。                                                                          |
| 其他条件 | 学历、毕业窗、首次就业、英语、成绩排名、专业代码、证书及回避等。未知项明确保留，不替用户判断已满足。                                |
| 工作取舍 | 培养轮岗、服务年限、营销指标、驻外/出差、倒班、合同/派遣/代理关系及发展路径。待遇未核不编造。                                       |

“相关专业”“理学”“经济类”只能作为确认线索；不能把应用统计专硕的学位门类或代码强行映射成招聘方接受的范围。“专业不限”只作用于有证据的岗位，不能扩展到同公告里的消防、法务、财会、医生、签派、硬件等有特定要求的岗位。

## 3. 单位不错的判断要可解释

说明规模化实际业务、直接用工主体、行业/区域平台、培养体系、业务相关性等至少一项可核验理由，并写出当前不知道的部分。不得用世界500强、国企二字或招聘广告薪资代替岗位质量判断，不作保录、保编制、保收入或永久稳定承诺。

银行业务、运营柜面、市场营销、管培、报表分析、综合管理可以纳入。是否涉及销售、初期柜面、长期服务、低固定高提成应如实说明，不替用户一刀切否定。保险岗位必须区分劳动合同员工与代理制业务员；尚未核到用工方式时写待核。

真正排除：已经确认存在无法满足的硬条件（例如博士限定、必需的特定执照/专业）、实际职责与候选人无合理关联且无不限专业机会、主体或招聘真实性无法成立。可修正的技能缺口和未明确的条件进入待核，不冒充已确认不合格。

## 4. 来源、日期与状态

优先级：官方职位与招聘公告/附件；用人单位在高校就业网发布的当届正文；官方索引/授权招聘平台；可信转载；往届记录。层级不是自动互换的。

高校正文是有价值的当届依据，但不能写成“官网动态 JD 已逐条核验”。模板元数据不能压过正文，附件未读、二维码入口未展开、原站打不开均需记录。只有旧公告时，不把年份替换成 2027；只见搜索摘要时，不臆补职位条件。不同页面冲突先分辨主体、批次和岗位，不能简单取早日期制造一个统一截止。

status 沿用数据库现有枚举：open 为本届公告/职位窗口开放；soon 为明确未来开放；verify 为本届有机会但条件/入口/冲突需核；watch 为跟进线索；past 为所记录窗口已过。open 不等于用户已通过专业或全部资格审查。页面的专业评估与批次是独立标签；旧卡片没有评估证据时显示待核。

截止仅写有明确信息的日期与时刻。只有“10月”“暂定10/18”“招满即止”时，在文字中保留，不伪装为确定倒计时。宣讲日期、网页下架日期、集团最终通道不当成个人岗位截止。核查时间统一北京时间；每次新增来源记录发布日、核查日、实际读取范围。整理旧资料不等于当日重新访问官网。

## 5. 数据与评估如何维护

- data/soe.json 是招聘事实维护源；使用现有 req 显示专业条件，window 显示届次/毕业窗，jobs、risk、action、evidence 写清职责、疑点和下一步。
- data/soe-screening.json 是配套评估源，以 ID 关联。每条记录包含 major、cycle、intake、directions、basis、qualityBasis、evidenceRefs、reviewedOn、basisHash。方向允许多选；界面、校验使用 src/soe-policy.js 的统一词表。
- basisHash 绑定专业/职责/毕业窗/批次/日期/来源等事实。变更事实后应先重新阅读证据和判断，再用 scripts/validate-screening.mjs 导出的 screeningDigest 生成摘要。严禁将重算摘要当作自动核查。
- 评估随前端构建发布，不新增 SQL 字段或更改用户状态表。浏览器发现云端事实与本次已审核快照不一致时，会降级为专业/届次待核，不能继续套用过期的肯定标签。
- 旧快照/云端缺少当前构建已收录的稳定 ID 时，不允许悄悄把新卡片覆盖掉；保留完整内置资料并提示待云端发布后重试。
- 来源采用稳定 ID；共享来源不可只改一页。保留 ORIGINAL_ITEMS 和原卡片 ID。修改准入规则不能给旧事实伪造新的核查日期。

## 6. 排序和验收

默认先比较批次与专业证据，再比较岗位参考优先级；支持按方向、专业证据、批次、个人状态、关键词和日期自行筛选。匹配分是维护者参考判断，不是录取概率，不应以“不做算法”自动降级。未知条件应触发核验动作，不应悄悄消失。

执行 npm run verify、完整 Git 基线 ID 校验和 git diff 检查。测试必须覆盖新增方向能被筛出、标签不会误套到变化后的云端事实、旧 ID/历史不丢失，以及统计/不限专业不等于资格保证。更新 README 与本次核查记录；没有用户明确授权，不推送或同步生产。

## 7. 地区偏好补充（用户最新要求）

杭州、成都、重庆、西安同档重点，浙江其他城市也加分，但任何地区都不是准入门槛。具体证据、同档加分、岗位方向交集、去重和维护方式见 [地区偏好规范](location-preferences.md)。对应数据在 data/soe-locations.json，和专业/届次判断独立校验。
